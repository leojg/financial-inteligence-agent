# v1.5 — Prompt and Model Optimization (Full Spec)

*Goal: use the v1.4 baselines to make targeted improvements to LLM output quality and reduce running costs, with every change measured against the eval framework.*

This milestone is experiment-driven. The specific changes depend on what the v1.4 baselines reveal. The deliverables are: the infrastructure to run model/prompt comparisons efficiently, a set of experiments against known weak spots, and documented results showing the quality/cost tradeoff for each change.

---

## Methodology

Every optimization follows the same loop:

1. Identify a target (low eval score, high cost node, known weak spot)
2. Formulate a hypothesis ("swapping normalize to gpt-4o will fix currency extraction", "adding few-shot examples to categorize will improve accuracy by 5%+")
3. Make exactly one change (prompt or model, not both)
4. Run the v1.4 eval suite against the change
5. Compare to baseline: quality delta and cost delta
6. Keep, revert, or iterate

One change at a time. If a prompt change and a model change both improve a node, test them separately first, then together. Compounding changes without isolating effects produces numbers you can't reason about.

---

## Infrastructure: comparison runner

**File:** `scripts/run_comparison.py` (or integrated into the eval suite)

The eval suite from v1.4 runs against one configuration. This milestone adds the ability to run the same test set against multiple configurations and produce a comparison table.

Input: a list of config overrides, each defining a model name and/or a prompt variant identifier.

Output: a markdown table (printed to stdout and optionally saved to `data/eval_comparisons/`) showing metrics side by side:

```
Normalization — currency exact match
──────────────────────────────────────────────
  baseline (gpt-4o-mini)          72%
  gpt-4o                          91%    +19%
  gpt-4o-mini + prompt v2         84%    +12%

Estimated cost per full reconciliation run
──────────────────────────────────────────────
  baseline (gpt-4o-mini)          $0.03
  gpt-4o                          $0.18   +500%
  gpt-4o-mini + prompt v2         $0.03   +0%
```

**Cost estimation:** each eval run tracks input/output token counts per node (LangChain callbacks or manual counting). Multiply by the model's per-token pricing. Does not need to be exact, ballpark is enough to compare options. Token counts are logged alongside quality metrics.

**Prompt variant management:** prompt variants are stored as named alternatives alongside the current prompt, not as git branches. The comparison runner selects which variant to use by name. This avoids branch juggling and lets you compare three prompt versions in a single script run.

Implementation options: prompt variants as separate string constants in a `prompts.py` file per agent, or as template files in a `prompts/` directory. The simplest approach is string constants with a registry dict keyed by variant name.

## Known targets

These are the experiments to run based on what is already known about the system. The v1.4 baselines will likely reveal additional targets.

### Reconciliation: currency extraction (high priority)

**Current state:** gpt-4o-mini extracts currency unreliably. The `$` symbol is ambiguous across Argentina, Uruguay, Colombia, Mexico, and the USA. Even with explicit prompt instructions to return null for ambiguous currency, the model infers from contextual clues. Pydantic field description examples ("e.g. USD, EUR, UYU") further bias the model toward guessing.

**Experiments:**

1. **Prompt: remove biasing examples from Pydantic field descriptions.** The "e.g. USD, EUR, UYU" in the field description teaches the model to always pick one. Removing it or replacing with "return null if ambiguous" may reduce false confidence. Cost: zero. Eval: normalization currency match rate.

2. **Prompt: explicit ambiguity instructions with examples.** Add few-shot examples to the normalization prompt showing cases where currency should be null ("$" with no other context) vs cases where it's deterministic ("R$" is always BRL, "€" is always EUR). Cost: marginal token increase. Eval: currency match rate, check that null rate increases for ambiguous cases without dropping for unambiguous ones.

3. **Model: gpt-4o for normalize node only.** Test whether the larger model handles ambiguity better. Cost: significant per-node increase (normalize runs once per document, but documents can be large). Eval: full normalization field-level accuracy. The question is whether the currency improvement justifies the cost increase, or whether a prompt fix on mini gets close enough.

4. **Hybrid: deterministic currency resolution post-LLM.** Not a prompt/model change but worth testing: let the LLM extract what it can, then apply deterministic rules based on account region, known currency per account, or explicit user config. This is the "deterministic-first, LLM-as-fallback" principle applied to currency. If the account is configured as UYU, any `$` amount from that account is UYU regardless of what the LLM says. This might make the LLM's currency accuracy less important.

### Reconciliation: categorization (medium priority)

**Current state:** 89.9% accuracy with lenient matching. After v1.4 tightens the eval, this number will drop. The LLM-inferred categories (no fixed taxonomy) means the model invents category names, which is flexible but inconsistent.

**Experiments:**

1. **Prompt: add few-shot examples.** Show 3 to 5 example transactions with their expected categories in the prompt. This anchors the model's category vocabulary without enforcing a fixed taxonomy. Cost: marginal token increase. Eval: categorization primary match rate.

2. **Prompt: category vocabulary anchor.** Instead of a full taxonomy, provide a "preferred categories" list as guidance, not a constraint. "When applicable, prefer these category names: Groceries, Dining, Transportation, Healthcare, Entertainment, Subscriptions, Utilities, Transfer, Salary, Education, Shopping, Fees & Charges, Other." The model can still deviate but has a shared vocabulary to gravitate toward. Eval: categorization accuracy + consistency across runs (run the same data 3 times, measure category name stability).

3. **Model: test Haiku for categorization.** Categorization is a classification task with relatively low complexity. If a smaller/cheaper model achieves similar accuracy, it's a free cost reduction. Eval: categorization accuracy + cost comparison.

### Reconciliation: duplicate detection (depends on v1.4 results)

Priority depends on how the harder test pairs perform. If precision/recall drop significantly with the new test data, prompt improvements to the LLM reasoning tier become important. If they stay high, this is low priority.

**Experiments (conditional):**

1. **Prompt: structured reasoning format.** The current duplicate prompt asks for JSON with is_duplicate, confidence, and reason. Adding explicit reasoning steps ("First, compare the merchant names. Are they the same business? Then compare dates...") may improve accuracy on fuzzy cases. Eval: duplicate precision/recall on fuzzy and LLM-tier pairs specifically.

2. **Prompt: few-shot examples of hard cases.** Show the model examples of merchant name variations that are duplicates ("NETFLIX" vs "NF *NETFLIX") and similar-looking transactions that are not ("UBER" on Jan 5 and "UBER EATS" on Jan 5, different amounts). Eval: duplicate precision/recall by tier.

### Insights: model and prompt (medium priority)

**Current state:** gpt-4o at temperature 0.0. Runs once per session so cost per invocation is acceptable, but if gpt-4o-mini can produce comparable quality, the savings compound over time.

**Experiments:**

1. **Model: gpt-4o-mini for generate_insights.** Run the v1.4 insights eval with mini instead of 4o. If coverage and faithfulness hold up, this is a straightforward cost reduction. If they drop, the gap quantifies what you're paying for with the larger model. Eval: insights coverage rate, faithfulness rate, severity accuracy.

2. **Prompt: structured output guidance.** The current prompt is relatively freeform ("analyze the spending data and return observations"). Adding more structure ("For each category above 15% of total spending, provide one habit observation. For any category with MoM increase above 20%, flag it with warning severity.") may improve coverage without a model change. Eval: insights coverage rate. Risk: over-constraining the prompt may produce mechanical output that misses emergent patterns.

3. **Prompt: few-shot examples.** Provide one example aggregation snapshot and its expected output directly in the prompt. Anchors the model's output format and depth. Cost: token increase (the example is ~200 to 300 tokens). Eval: all insights metrics.

### Chat: model routing (from backlog, medium priority)

**Current state:** gpt-4o for all questions. Most user questions are simple single-tool lookups ("how much did I spend on groceries?") that gpt-4o-mini could handle.

**Experiments:**

1. **Baseline: gpt-4o-mini for all chat.** Before building routing, test whether mini handles the full question set acceptably. If tool selection accuracy and response faithfulness stay high, routing is unnecessary, just use mini. Eval: chat tool selection accuracy, response faithfulness.

2. **Routing: classifier-based.** If mini fails on complex questions but succeeds on simple ones, add a lightweight classifier (could be a mini call itself, or rule-based on question length/keywords) that routes simple questions to mini and complex ones to 4o. The v1.4 chat eval labels include question categories that map naturally to simple vs complex. Eval: tool selection accuracy by question category, cost per question.

3. **Prompt: tool descriptions.** Better tool descriptions may improve tool selection accuracy independently of model choice. If `get_spending_by_category` has a clearer description, the model picks it more reliably. This is a zero-cost improvement. Eval: chat tool selection accuracy.

## Deliverables

1. **Comparison runner infrastructure** — script or eval extension that runs the same test set against multiple configs and produces side-by-side metrics with cost estimates
2. **Prompt variant management** — named prompt alternatives per node, selectable by the comparison runner
3. **Experiment results** — documented comparison tables for each experiment run, saved to `data/eval_comparisons/` or `docs/`
4. **Updated configs** — any model or prompt changes that improved metrics are merged into the default configs, with the comparison data as justification
5. **Cost baseline** — estimated per-run cost for the full reconciliation pipeline, insights pipeline, and per-chat-message, documented as a reference for future optimization

---

## Does not deliver

- New features or architectural changes (this is purely quality/cost optimization on existing nodes)
- Vision model optimization (deferred, separate cost/complexity profile)
- Chat message persistence or summarization (separate milestone, architectural change)
- Automated cost monitoring in production (out of scope, this is eval-time cost estimation only)

## Acceptance criteria

- At least one node shows measurable quality improvement (higher eval score) or cost reduction (lower token cost at equivalent quality) vs v1.4 baseline
- Every change merged into default config has a documented comparison table showing the before/after
- No node regresses below v1.4 baseline thresholds
- The comparison runner can be re-run by anyone with API keys in under 10 minutes
