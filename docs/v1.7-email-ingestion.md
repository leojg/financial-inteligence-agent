# v1.7 — Email Ingestion (Full Spec)

*Goal: read financial emails from Gmail — statements sent as PDF attachments and per-movement notification emails — so statements no longer have to be uploaded by hand and the current month is visible before its statement arrives.*

Until this ships, statements are uploaded manually (UI, API or MCP). The system reads no email today.

**Depends on v1.6** (`docs/v1.6-statement-accuracy.md`): attachments go through its PDF extraction, and notifications are checked against its `Statement` rows. Principle numbers below refer to v1.6 §2.

**Scope:** Gmail only. Other providers (IMAP) are out of scope until needed; the code sits behind an interface so one can be added without touching the rest.

---

## 1. Two kinds of email

| Kind | Example | Handling |
|---|---|---|
| Statement delivery | the monthly statement as a PDF attachment | The attachment goes through the v1.6 PDF path like an uploaded file; the email is only transport |
| Notification | a per-movement alert in the body: purchase, transfer, payment | A new `email_body` document that produces **provisional** transactions (§2) |

An email can be both, or neither (marketing from the same sender). Neither is recorded in the ledger as `ignored` with a reason, not dropped silently (principle 6).

---

## 2. Notifications: provisional rows and the cross-check

Notifications are not statements — no balance, no period — but they arrive early and independently of the statement, which makes them useful twice.

- **Provisional rows:** a notification creates a transaction with `source_kind = notification` and `provisional = true`, so the current month shows up before its statement arrives. Reports label these rows as provisional and count them separately.
- **Cross-check of statement extraction:** when the statement covering that account and period lands, each notification is matched to a statement row deterministically — account last 4, currency, amount, date within a few days, then merchant similarity.
  - Matched → the statement row is the record; the notification is linked to it (`confirmed_by`) and never counts as a second expense.
  - Still unmatched once its statement is in → excluded from totals (the statement is the truth) and listed as a diagnostic: either the statement extraction missed a row or the charge was reversed. This is an accuracy signal for v1.6 that needs no labels.
  - Statement rows without a notification are normal — not every movement sends an email.
- **Totals:** a provisional row counts only while no statement covers its account and date.

**Parsing bodies:** per-sender templates on the email's text (deterministic, like v1.6's PDF profiles), with v1.6's hardened LLM rung as fallback under the same transcribe-only contract. A known sender whose template stops matching is a diagnostic, not silence — templates change without notice.

---

## 3. Fetching from Gmail

- **Access:** Gmail API, OAuth installed-app flow, scope `gmail.readonly`. The mailbox is never modified (no labels, no read flags), so read-only is enough. The OAuth client file and token live in a local, gitignored path given by env; never in the DB or git.
- **Polling, not push:** a scheduled poll with a bounded query — the sender allowlist plus `after:` the last successful poll minus an overlap window. A push connection can stop firing without any error; a poll that fails is visible.
- **Incremental sync:** after the first full query, use `history.list` from the last stored `historyId`; when Gmail answers that the id is too old (404), fall back to the bounded query.
- **Ledger:** processed state lives in our DB, in an `email_messages` table — Gmail message id, SHA-256 of the raw message, sender, received date, kind, status (`pending` / `done` / `failed` / `ignored`), reason, attempts.
- **Done means written:** a message is marked `done` only after its rows (or its statement) are written. One whose attachment or body failed stays `pending` and is retried up to a cap, then `failed` with the reason — never marked done just because it was fetched.
- **Re-fetching is harmless:** the content-hash identity (principle 13) and the ledger make the overlap window safe.
- **Health:** each poll records its time and per-sender counts. No successful poll for a day, or a sender that usually writes and has gone quiet for N days, is a diagnostic in the run summary.

---

## 4. Security — email is untrusted input

- **Who may create transactions:** a sender allowlist per institution, and the message must pass DKIM (and SPF) per the `Authentication-Results` header that Gmail itself added (`mx.google.com`). Headers further down the message can be written by anyone and are ignored. A spoofed "bank" email creates nothing and is logged as `ignored`.
- **LLM boundary:** bodies reach the LLM only on the fallback path, as data, with no tool access.
- **Links are never followed.** A statement only available behind a link is a diagnostic telling the user to download and upload it.
- **Encrypted PDFs:** if an institution sends password-protected statements, the password comes from local secrets (env), never from the DB or git.
- **Private data:** sample emails for templates and tests live under `PRIVATE_EVAL_DIR`, never in the repo — this repo is public.

---

## 5. Placement

- `src/integrations/email/` with an `EmailSource` interface (list new messages since a cursor, fetch one raw message) and a `GmailSource` implementation.
- A poller command (`python -m integrations.email.poll`) that runs one poll: attachments are written to an inbox folder and passed to the existing `reconciliation.run(files=...)` service; bodies go in as `email_body` documents.
- A compose service behind `--profile email` runs the poller on an interval, following the existing `api` / `mcp` / `n8n` profiles. The n8n integration remains an alternative transport, not a requirement.

---

## 6. Phases

1. **Gmail access + ledger.** OAuth setup, `GmailSource`, `email_messages`, the bounded poll, health diagnostics. Output: every allowlisted message in the ledger, nothing processed yet.
2. **Statement attachments.** Attachments through the v1.6 PDF path; `done` only after the statement is written.
3. **Notifications.** Per-sender templates + LLM fallback, provisional rows, the notification ↔ statement cross-check and its diagnostics.

---

## Open questions

1. **Which senders** send statements and which send notifications? This decides the allowlist and the templates; sample emails are needed for each.
2. **Polling interval:** how fresh the current month needs to be (minutes vs. hours).

---

## Does not deliver

- Providers other than Gmail
- Following links in emails to download statements
- Sending email (digests, alerts) — the n8n *Email → Reconcile → Notify* workflow stays in the backlog
- UI for provisional rows and unmatched notifications (stage 2)

## Acceptance criteria

- Every allowlisted email is in the ledger with a status and, when not `done`, a reason.
- No message is marked `done` before its rows or statement are written.
- A message failing DKIM, or from a sender outside the allowlist, creates no transaction.
- Every notification is matched to a statement row, waiting for its statement, or listed as unmatched; none is counted twice.
- A poll that cannot reach Gmail, or a sender gone quiet, shows up in the run summary.
