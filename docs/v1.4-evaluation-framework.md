# v1.4 — Evaluation Framework (Full Spec)

*Goal: establish reliable baselines for every LLM-dependent node across all three graphs so that model and prompt optimizations can be measured, not guessed.*

The existing eval suite covers categorization accuracy (89.9%) and duplicate detection precision/recall (100%/100%), but the test data is too easy, the matching criteria too lenient, and most LLM nodes have no eval coverage at all. The 100% duplicate scores are a red flag, not a victory, the synthetic pairs only exercise the trivial exact-match tier and never stress the fuzzy or LLM reasoning tiers.

This milestone hardens the evaluation framework into something you can trust, so the next phase (model and prompt optimizations) has honest numbers to improve against.

## 1. Improved synthetic data generation

**File:** `scripts/generate_samples.py`

The generation script is the foundation. Every reconciliation eval improvement depends on better labeled data.

### 1.1 Normalization labels (new section in `eval_labels.json`)

For each generated file, emit the expected transactions with all fields:

```json
"normalization": [
  {
    "source_file": "data/itau_corriente_202601.xlsx",
    "file_type": "xlsx",
    "expected_transactions": [

        "merchant": "SUPERMERCADO DISCO",
        "amount": -2840.00,
        "currency": "UYU",
        "account": "Itaú Corriente"
      }
    ]
  }
]
```

Labels derived directly from the ground-truth constants already in the script, no manual duplication.

### 1.2 Harder duplicate pairs

The current pairing logic only matches exact merchant string + exact amount. The transaction constants themselves need new entries designed to stress each detection tier.

**Cross-bank merchant aliases (true duplicates):**
The same real-world purchase appears with different merchant strings across banks. Requires a merchant alias mapping in the generation script.

| Account A | Account B | Notes |
|---|---|---|
| NETFLIX | NF *NETFLIX | Prefix variation |
| UBER *EATS | UBER EATS | Separator variation |
| FARMACIA SAN ROQUE | SAN ROQUE FARM. | Abbreviation |
| MercadoLibre | MELI *MercadoLibre | Platform prefix |

Same date, same amount, different merchant string. True duplicates that should hit the fuzzy or LLM tier.

**Fuzzy amount pairs (true duplicates):**
Same merchant, same date, amount differs slightly (bank fee or rounding). For example, $50.00 in one account and $50.75 in another. Should hit the fuzzy tier.

**Temporal edge cases (true duplicates, borderline):**
Same merchant, same amount, 4 to 5 days apart across different accounts. Credit card processing delays make this realistic.

**False positive bait (non-duplicates):**
Same amount, same date, different merchants. Two $50 charges on the same day at unrelated stores. Must not be flagged.

**Recurring same-merchant non-duplicates:**
Netflix $15.99 on January 8 and Netflix $15.99 on February 8 in the same account. Same merchant and amount, different months. Not duplicates.

**Targets:** at least 8 to 10 true duplicate pairs spanning different difficulty tiers, and 25 to 30 non-duplicate pairs including false positive bait patterns.

### 1.3 Harder categorization labels

Add ambiguous merchants to the transaction constants: gas station convenience stores, pharmacies that sell groceries, hotels (travel vs dining depending on charge type).

Add an `alternatives` field for genuinely ambiguous merchants:

## 2. Reconciliation graph evals

### 2.1 Normalization eval (new)

**File:** `tests/eval/test_normalize_eval.py`

Evaluates the normalize node in isolation. Feeds RawDocument objects built from the generated file content, runs `make_normalize_node(config)(state)`, compares output Transaction fields against normalization labels.

**Metrics (field-level):**
- Date exact match rate
- Merchant exact match rate (case-insensitive, trimmed)
- Amount exact match rate (within floating point tolerance, 0.01)
- Currency exact match rate (reported separately, known weak spot with gpt-4o-mini and ambiguous `$`)
- Overall field accuracy (all four fields correct for a transaction)

**Thresholds:** set after first baseline run. The point is to establish the numbers, not assert arbitrary targets.

Uses the same model as production (configured via `ReconciliationConfig`). Model is a parameter so the optimization phase can run the same test set against different models.

### 2.2 Duplicate eval (rewrite)

**File:** `tests/eval/test_duplicate_eval.py`

Structure stays the same (union-find clustering, precision/recall), but receives much harder pairs from the improved labels.

**Changes:**
- Metrics broken down by difficulty tier (exact match pairs, fuzzy pairs, LLM-reasoning pairs) in addition to aggregate. Shows which tier is failing rather than hiding it in an average.
- Tier-hit diagnostic: for each labeled pair, log which detection tier actually resolved it (fingerprint, fuzzy, LLM). If all pairs resolve at the fingerprint tier, the harder tiers are untested regardless of score.
- Non-duplicate pair count increased to 25 to 30 for metric stability (at 10 pairs, one false positive is a 10% precision drop).

### 2.3 Categorization eval (revision)

**File:** `tests/eval/test_categorize_eval.py`

**Changes:**
- Tighten the semantic equivalents map. Remove broad matches like "Healthcare" matching "Fitness". Keep only true synonyms where either answer is equally correct (e.g., "Salary" and "Income").
- Alternatives-aware scoring: if the label has an `alternatives` field, match against alternative counts as partial. Report three numbers: primary match rate, alternative match rate, miss rate.
- Let accuracy drop to reflect reality. A lower honest number is the goal.

### 2.4 Suspicious activity eval (new)

**File:** `tests/eval/test_suspicious_eval.py`

Feeds the full transaction list (context + test cases) to `make_flag_suspicious_node(config)(state)` because the node reasons about patterns relative to the overall profile.

**Metrics:**
- Recall on `should_flag` transactions
- Precision on `should_not_flag` transactions
- Broken down by pattern type (outlier, rapid-fire, round number)

**Thresholds:** set after first baseline run.

## 3. Insights graph eval

### 3.1 `compute_aggregations` unit tests

**File:** `tests/unit_tests/test_aggregations.py`

This node is pure Python with no LLM. Standard deterministic tests, not part of the LLM eval suite.

Build known transaction sets in the database, run `compute_aggregations`, assert expected output values: spending by category totals, month-over-month deltas, recurring charge detection, transfer fee summaries. This is the quickest win in the milestone.

### 3.2 `generate_insights` eval (new)

**File:** `tests/eval/test_insights_eval.py`

The only LLM node in the insights graph. Output is structured (`InsightsOutput` with `Habit` and `Suggestion` models) but qualitative, so exact match evaluation does not apply. The node uses `with_structured_output(InsightsOutput)` and temperature 0.0.

The evaluation uses two layers: deterministic coverage checks (no extra LLM cost) and an LLM-as-judge faithfulness check (catches hallucinated numbers).

**Test set:** 3 to 5 curated aggregation snapshots, each a hand-crafted dict with no DB dependency. The node is tested in isolation.

| Profile | Description | Goals | Key signals in data |
|---|---|---|---|
| Overspending | Dining is 48% of spending, jumped 63% MoM | "Reduce restaurant spending", "Save 20% of monthly income" | Dining dominance, large MoM spike, 6 recurring subscriptions at $99/month |
| Healthy | Balanced categories, slight MoM decrease | "Save 20% of monthly income" | No alarming patterns, savings goal on track |
| Dramatic shift | One category jumped 30%+ MoM, others stable | None | Must identify which category drove the shift |
| Recurring bloat | 8 subscriptions totaling 15% of income | None | Must flag subscription count, suggest review |
| Minimal data | Only 2 weeks of transactions, sparse categories | "Reduce restaurant spending" | Should acknowledge limited data, avoid overconfident conclusions |

Each profile defines its aggregation dict, goals_prompt, and evaluation criteria:

```python
{
    "id": "overspending",
    "date_from": "2026-01-01",
    "date_to": "2026-01-31",
    "goals_prompt": "Reduce restaurant spending\nSave 20% of monthly income",
    "aggregations": { ... },  # full synthetic aggregation dict
    "expected_coverage": [
        {"field": "habits", "must_reference": "Dining", "reason": "Dining is 48% of spending and jumped 63%"},
        {"field": "suggestions", "must_reference": "Dining", "reason": "User goal explicitly targets restaurant spending"},
        {"field": "habits", "must_reference": "recurring", "reason": "6 subscriptions at $99/month"},
    ],
    "severity_floor": {
        "Dining": "warning"  # 63% increase should not be labeled "info"
    }
}
```

**Layer 1: Deterministic coverage checks (no judge, no extra LLM cost)**

Given the structured output, assertions check whether the output addresses what the data obviously shows:

- `expected_coverage`: for each entry, scan the specified field's items (habits or suggestions) for the keyword in `category`, `observation`, `title`, or `body` (case-insensitive). At least one item must reference it.
- `severity_floor`: for habits matching a given category, assert severity is at least the specified level (`info` < `warning` < `critical`).
- Goal relevance: if a goal is present and the aggregation data supports it (e.g., "reduce restaurant spending" + restaurants are a top-3 category), at least one suggestion must reference it. If the data does not support the goal (e.g., restaurant spending is 2%), no suggestion should prioritize it.
- No-goals profile: verify the output does not hallucinate goals or reference goal-related language when `goals_prompt` is None.

**Layer 2: LLM-as-judge faithfulness check (catches hallucinated numbers)**

The deterministic layer cannot catch whether specific numbers in the output text are correct. If `spending_by_category` shows Dining at $1,800 but a habit says "you spent $2,400 on dining", that is a hallucination.

A judge model receives the aggregation input, the generated output (habits + suggestions), and checks whether every specific number or percentage mentioned in `observation` and `body` fields traces back to a value in the aggregations. Returns a per-item faithfulness score (faithful / unfaithful / no-numbers).

The judge is a separate model from production. It only runs on the output, not on the full aggregation prompt, so cost is low (3 to 5 judge calls per eval run).

**Metrics reported:**
- Coverage rate: percentage of `expected_coverage` items matched
- Severity accuracy: percentage of severity assertions passed
- Goal relevance: pass/fail per profile
- Faithfulness rate: percentage of output items with no hallucinated numbers (from judge)

**Thresholds:** set after first baseline run.

## 4. Chat graph eval

### 4.1 Tool selection eval (new)

**File:** `tests/eval/test_chat_tool_selection.py`

The most straightforward chat eval. Given a user question, does the agent pick the right tool(s)?

**Test set:** 15 to 20 questions spanning the tool surface:

| Category | Example question | Expected tool(s) |
|---|---|---|
| Category spending | "How much did I spend on groceries?" | `get_spending_by_category` |
| Recurring charges | "What subscriptions am I paying for?" | `get_recurring_charges` |
| Merchant drill-down | "Show me all transactions at Netflix" | `get_transactions_by_merchant` |
| Date-scoped | "What did I spend last month?" | `get_spending_by_category` (with date params) |
| Multi-tool | "Compare my grocery spending to dining" | `get_spending_by_category` (multiple calls or params) |
| Goal-related | "Am I on track with my savings goal?" | Context-based (no tool, uses aggregations in prompt) |
| Out-of-scope | "What's the weather?" | No tool call, polite decline |
| Out-of-scope | "Help me write an email" | No tool call, polite decline |

**Metrics:** tool selection accuracy (correct tool called / total questions). For multi-tool questions, all expected tools must be called.

**Method:** run the chat graph for a single turn per question, intercept the tool calls (or lack thereof), compare against labels. The response content is not evaluated here, only the tool selection.

### 4.2 Response faithfulness and out-of-scope eval (new)

**File:** `tests/eval/test_chat_response_eval.py`

Two failure modes beyond tool selection:

**Response faithfulness:** the agent calls the right tool but misinterprets the result. The tool returns $350 for grocery spending but the agent tells the user $500. LLM-as-judge comparing the tool output to the final response text.

- Reuse a subset of the tool selection test set (the ones where the right tool was called).
- For each, capture the tool output and the final response.
- Judge model scores faithfulness: does the response accurately reflect the tool output? Are numbers correct? Are no claims made that the tool data does not support?

**Out-of-scope handling:** for the out-of-scope questions from the tool selection set, verify the response is a polite decline and does not hallucinate data or call an irrelevant tool.

**Thresholds:** set after first baseline run.

## Does not deliver

- Model or prompt optimizations (this milestone establishes baselines, the next milestone improves them)
- Vision/image extraction eval (deferred, higher cost, added incrementally once text-based eval is proven)
- End-to-end multi-graph eval (node-level baselines first)
- Multi-turn chat coherence eval (deferred until message persistence is in place)

## Acceptance criteria

- `make eval` runs all eval tests (normalize, categorize, duplicates, suspicious, insights, chat tool selection, chat response) against real LLM calls
- Each test prints a metrics table with per-category breakdowns
- Duplicate eval reports which detection tier resolved each pair
- Categorization eval reports primary vs alternative vs miss rates
- Baseline numbers documented as the reference point for the optimization phase
- Duplicate precision/recall numbers are no longer 100%, if they still are, the test data is still too easy
