# v1.6 — Statement Extraction Accuracy (Full Spec)

*Goal: make the numbers extracted from real bank and card statements trustworthy enough to build a multi-month expense report and spending profile on top of them — and make every remaining error visible instead of silent.*

The pipeline works end to end, but on real statements the extracted transactions were not accurate enough to trust. The v1.4 normalize eval does not show this: it scores 100% (README, *Latest full run snapshot*) because the synthetic statements are far cleaner than real ones. This milestone changes how statements are read and, above all, how a reading is **checked**.

UI work (review screens for mismatches, report pages) is stage 2 and out of scope here; this milestone only needs the review data to exist.

---

## 0. Why the current eval cannot see the problem

`scripts/generate_samples.py` produces statements where every row has an ISO date, a signed dot-decimal amount, an explicit currency and the account name, each file is one page, and every description is one line. A model reads that perfectly. Real Uruguayan statements look different:

- `dd/mm/yyyy` dates, `1.234,56` amounts, sometimes `1,234.56` in the same bank's USD export
- separate **Débito / Crédito** columns (one of them blank per row) and a running **Saldo** column
- several pages, with the header ("Moneda: $", account number, period) only on page 1 and repeated column headers / page footers on every page
- descriptions that wrap onto a second line
- credit cards with **UYU and USD columns side by side**, a previous balance, payments, installments (`CUOTA 3/6`), interest and fees
- legacy `.xls` exports and multi-sheet workbooks

A 100% score on clean data says nothing about these cases. The synthetic set stays (it is the CI-friendly regression net), but it cannot be the accuracy number.

## 1. Failure modes in the current pipeline

Found by reading the code and running the parsers on the sample files. Each one is a way a real statement turns into wrong numbers in the report.

| # | What happens | Where | Effect on the report |
|---|---|---|---|
| F1 | Each PDF **page** is normalized in its own LLM call; the prompt says "if no currency is stated, default to `base_currency`" (USD). Page 2+ of a UYU statement usually has no currency line. | `parsers.py:57` (one Document per page), `nodes.py:244`, `nodes.py:263-264`, `configuration.py` (`base_currency="USD"`) | UYU rows booked as USD → amounts off by ~40× |
| F2 | PyPDF text puts every table cell on its own line; column position is lost. With Débito/Crédito columns, a blank cell is invisible, so the model guesses which column a number came from. | `parsers.py:57` | Sign errors: expenses read as income and vice versa |
| F3 | A response that fails `json.loads` (or any other exception) skips the **whole document** with a log warning. No structured output, no count. | `nodes.py:297-304` | Whole statements silently missing |
| F4 | `.xls` files need `xlrd`, which is not installed; the error is swallowed. Only the first sheet of a workbook is read. | `parsers.py:22`, `parsers.py:37-38` | Exports silently missing |
| F5 | Nothing checks the extracted rows against the statement's own arithmetic (opening balance + movements = closing balance, running Saldo). | — | No way to know a statement is wrong |
| F6 | Opening/closing balance rows (`SALDO ANTERIOR`, `SALDO FINAL`) are extracted as transactions — and the labels say that is correct (`SALDO ANTERIOR` → "Other Income"). | `generate_samples.py:73`, `:93` | Opening balance counted as income |
| F7 | Statement **images** collapse to one row: the vision prompt asks only for a receipt summary, and each image becomes a single-row table. All images go in one call with index-aligned results and a shared 4096-token budget. The normalize eval skips images, so this is never measured. | `nodes.py:107-150`, `:182-227`, `test_normalize_eval.py` (`_SUPPORTED_FILE_TYPES`) | A 56-row statement screenshot yields 1 row; one extra receipt in an image shifts every later result |
| F8 | PDF/XLSX documents get `confidence=1.0` hardcoded, so the low-confidence review never fires for them. | `nodes.py:76` | No review path for text documents |
| F9 | The normalized-document cache is keyed only by the hash of the extracted text. A bad extraction is replayed forever; prompt or model changes do not invalidate it. | `nodes.py:248` | Fixes don't reach already-seen statements |
| F10 | Expense = `amount_base < 0 AND duplicate_of IS NULL`. Transfers between the user's own accounts and the card bill paid from checking are counted as spending; rows whose currency conversion failed (`amount_base` NULL) drop out silently. | `database_repository.py:424` (and the other aggregation queries) | Expenses double-counted; some silently excluded |

## 2. Design principles

The rules the design in §3 follows. They are referenced by number below.

1. **Trust order: structured export > deterministic reader > LLM.** Where a structured export exists it wins; a deterministic per-layout reader comes next; the LLM is the fallback for layouts nobody has written a reader for. A bank has only a handful of statement layouts, detectable by printed labels and readable with columns located by the header row rather than by fixed position, so per-bank readers are cheap and pay off.
2. **A statement is accepted only if its own arithmetic closes.** Bank balances are exact to the cent: opening balance + Σ movements = closing balance, and every row's running balance follows from the previous one. A statement that doesn't close is kept as `mismatch` — never dropped and never "fixed" with invented rows.
3. **Arithmetic resolves ambiguous numbers.** `4.000` can be four or four thousand. The parser returns every plausible reading and lets the balance arithmetic pick the one that closes, instead of defaulting to one reading.
4. **Raw beside parsed; unparsable is NULL, never zero.** Every parsed number is stored next to the exact string it came from. A value that can't be parsed is NULL and counted — an invented zero hides the error and corrupts totals.
5. **The sign comes from structure, not from the model.** From the Débito/Crédito column, a CR/DB marker, or the running balance — not from a sign the LLM chose.
6. **What is discarded is counted.** Every run reports what it excluded, by reason, with count and amount. An empty result is an error, not "no changes". A retry that reports success is not recovery — count what reached the write.
7. **Text layer and image fail differently; send both.** The text layer gives exact strings but loses layout (columns, superscripts, which cell is blank); the image gives layout. For layout-sensitive extraction, giving the model both beats either alone.
8. **Anchor LLM output to the text layer.** A long, discriminating value the model returns (account number, closing balance) must appear in the document's text, or the result is rejected. Short numbers prove nothing — they appear in any digit string.
9. **The prompt must say *where* each field is, not just *which* fields exist.** Explicit rules — columns follow the header, one array element per printed row, local separators in and dot-decimal out — instead of a bare list of fields.
10. **LLM self-reported confidence is not a gate, and cached LLM answers are not ground truth.** Self-reported confidence is poorly calibrated, so gate on arithmetic instead.
11. **Test on the whole document.** Models can silently drop pages of long documents, so benchmark on full statements, not excerpts, and check row counts per page.
12. **Matching totals can hide errors that cancel out.** Compare statement by statement and row by row, not only the aggregate.
13. **Identity is the file's bytes, then a business key.** SHA-256 of the file before extraction for "have I seen this file"; a separate business key for "is this the same statement" — the same period can arrive twice in different formats.

## 3. Design

### 3.1 The statement is a first-class object

Today a statement is just a source of `Transaction` rows; nothing records what the statement itself says. Add a `Statement` model and `statements` table:

| Field | Notes |
|---|---|
| `id`, `file_sha256` | SHA-256 of the file bytes, computed before parsing (principle 13) |
| `institution`, `account`, `account_type` | `deposit` (caja de ahorros / cuenta corriente) or `card` |
| `currency` | Per statement; a card statement has one `Statement` section per currency |
| `period_start`, `period_end` | As printed |
| `opening_balance`, `closing_balance` (+ `_raw`) | As printed; NULL if the statement doesn't show them |
| `printed_totals` | Footer totals when present (total débitos/créditos, total compras, pagos) |
| `extractor`, `extractor_version` | Which rung of §3.3 produced the rows |
| `balance_status` | `ok` / `mismatch` / `no_balance` (§3.2) |
| `diagnostics` | JSON: rows dropped, pages with zero rows, parse failures — each with reason |

`Transaction` gains `statement_id`, `page`, `row_index`, `raw_text`, `amount_raw`, `balance_raw`, `balance_after`, `kind` (§4), and `sign_source` (`column` / `marker` / `balance` / `llm`). Balance rows (`SALDO ANTERIOR`, `SALDO FINAL`) populate the statement fields and are **not** transactions (fixes F6).

### 3.2 The balance check — the core of this milestone

It is a label-free accuracy test that runs on every real statement, every time:

- **Statement closes:** `opening + Σ credits − Σ debits == closing`, per currency, exact to the cent (`Decimal`, no tolerance — bank balances are not rounded).
- **Running balance chain** (when a Saldo column exists): for each row, `balance[i-1] + amount[i] == balance[i]`. This does more than pass/fail:
  - a break at row *i* points at the exact row;
  - if `balance[i-1] − |amount[i]| == balance[i]`, the row is a debit — **the sign is derived, not guessed** (fixes F2 even when the model got it wrong);
  - if no sign fits, the gap `balance[i] − balance[i-1] − amount[i]` is the amount of a missing row (or a misread one).
- **Card statements:** `previous balance + purchases + fees/interest − payments − credits == new balance`, per currency; printed totals per section when present.
- **Footer totals** (when printed): Σ debits and Σ credits match the printed totals.

Outcomes go to `balance_status`. `mismatch` is kept (principle 2), shown in the report as unverified, and routed to review with the rows that break the chain. `no_balance` (exports without balances) is accepted but counted and reported as lower trust.

LLM confidence stops being the gate for statements (principle 10); `image_low_confidence_threshold` stays for receipts only.

### 3.3 Extraction ladder

Each statement goes down the ladder until a rung produces rows **and** passes the balance check. A rung that fails falls through to the next; the last rung's output goes to review.

1. **Structured exports (XLSX / XLS / CSV) — deterministic, no LLM.** Find the header row by column names (`Fecha`, `Descripción`/`Concepto`, `Débito`, `Crédito`, `Importe`, `Saldo`, `Moneda`), never by position; read every sheet; parse numbers and dates in code (§3.4). Statement header fields come from the rows above the table. Add `xlrd` for `.xls` (F4).
2. **Per-bank PDF profiles — deterministic.** Use word coordinates (`pdfplumber`) rather than flattened text, so Débito vs Crédito is decided by x-position. A profile is data, not a class per bank: how to detect the bank (printed labels), the header row, which lines to skip (page headers, `Página n de m`, balance rows), how wrapped descriptions join, where the opening/closing balance are. Unknown layout → the next rung, counted as "no profile".
3. **LLM — hardened (for layouts without a profile, and images).**
   - **Transcribe, don't interpret** (principles 4, 5, 9): the model returns the statement header and one element per printed row with the cells as printed — `date_raw`, `description_raw`, `debit_raw`, `credit_raw`/`amount_raw`, `balance_raw`. Python parses numbers, dates and signs. Use structured output (JSON schema) instead of free-form JSON.
   - **Whole-statement context** (F1): the header (institution, account, currency, period, balances) is extracted once and passed to every page. Currency **never** defaults to `base_currency`; if neither the header nor the account profile gives it, it is NULL and the statement goes to review.
   - **Text + image** (principle 7): send the page image alongside a layout-preserving text layer. Compare against sending the PDF natively.
   - **Anchors and counts** (principles 8, 11): the account number and closing balance the model returns must appear in the text layer; rows per page are compared with a deterministic count of date-led lines; a page with zero rows is a diagnostic, not silence.
   - **Targeted retry:** when the chain breaks, re-ask for the failing page with the discrepancy stated (which rows, what gap). Once. Still failing → `mismatch` + review.
   - **Statement images** go through this rung with a statement prompt and one call per image (F7). Receipt extraction stays as is.
4. **Review.** Statement-level, with the breaking rows highlighted. (The data lands here; the screen is stage 2.)

### 3.4 Parsing numbers, dates and signs — in code

One module (`shared/parsing.py`), unit-tested, used by every rung:

- **Numbers:** both separators → the last one is the decimal; a lone comma is a decimal unless it matches `\d{1,3}(,\d{3})+`; `\d{1,3}(\.\d{3})+` is thousands — but with one dot and three digits both readings are returned and the balance chain picks (principle 3). Unparsable → NULL plus the raw string kept.
- **Dates:** `dd/mm/yyyy`, `dd/mm/yy`, `dd-mm-yyyy`, ISO; a date outside the statement period is a diagnostic. Statements are day-first; never `mm/dd`.
- **Currency:** `$`, `$U`, `UYU`, "Pesos" → UYU; `US$`, `U$S`, `USD`, "Dólares" → USD — applied to statement headers and column headers, where the context makes `$` unambiguous. Bare `$` on a receipt stays NULL, as today.
- **Signs:** from the Débito/Crédito column, a `CR`/`DB` marker, or the balance chain, recorded in `sign_source`. An LLM-chosen sign is the last resort and is flagged.

### 3.5 No silent loss

- Every failure path writes to `Statement.diagnostics` (or a per-run list for files that never became statements): reason, file, page, count and amount where known (fixes F3, F4).
- The run summary reports: statements by `balance_status`, rows by extractor rung, everything excluded and why, and the sum of amounts with no `amount_base`.
- A file that yields zero rows is an error, not an empty statement.

### 3.6 Caching

- Key: `file_sha256 + extractor_version` (+ model and prompt id on the LLM rung) (fixes F9).
- Only results with `balance_status = ok`, or confirmed by a person, are cached as truth (principle 10). A `mismatch` is re-extracted on the next run.

## 4. Expense-report correctness

Correct rows still produce a wrong expense report if every negative amount counts as an expense (F10). Each transaction gets a `kind`: `purchase`, `income`, `refund`, `fee`, `interest`, `transfer_out`, `transfer_in`, `card_payment`, `cash_withdrawal`.

- **Own-account transfers:** an outflow from one of the user's accounts and an inflow of the same amount into another within a few days (FX-adjusted across currencies) are paired as `transfer_out`/`transfer_in` and excluded from expense and income. Unpaired candidates go to review rather than being guessed.
- **Card payments:** the payment line on the card statement is paired with the debit in the paying account; both become `card_payment`. Spending is counted once, at the card's purchase lines.
- **Same statement twice** (PDF and XLSX of the same month, overlapping exports, or the same PDF uploaded and emailed): same account + period overlap → rows matched deterministically on date, amount, raw description and balance, not through the LLM duplicate tier.
- **Unconverted amounts:** reported as their own line ("N rows, X UYU not converted"), never dropped from the totals silently.

Aggregation queries filter on `kind` instead of `amount_base < 0`.

### 4.1 Installments (`CUOTA n/m`)

Decided: **each cuota is an expense in the month it is billed.** It is what the card statement shows, so the balance check (§3.2) closes without adjustment, and it works with partial history — a cuota 3/6 for a purchase made before the loaded months has no cuota 1 to attach a full purchase to.

In this milestone:

- Each cuota row keeps `installment_n` and `installment_m` as printed (part of the transcription, §3.3).
- Recurring-charge detection excludes installment rows. Today a 6-cuota purchase at a stable amount is indistinguishable from a subscription (`insights/tools.py:120-127`), so the spending profile would list it as one.

Follow-up (backlog, *Installment plan totals*): linking the cuotas of one purchase into a plan, a **committed** line (remaining cuotas × amount), a purchase-date view, and splitting interest surcharges.

### 4.2 Report currency

USD stays the default and becomes configurable:

- A `BASE_CURRENCY` setting (env, default `USD`) replaces the code-only default (`configuration.py:15`).
- Every converted row records `fx_rate`, `fx_date` and the currency it was converted to. Today queries sum `amount_base` across all runs with no currency check (`database_repository.py:421`), so changing the base currency between runs would add USD and UYU into one total.
- Reports convert from `amount_original` to the configured currency with the stored rate, so changing the setting does not require re-extraction. `amount_original` + `currency` remain the source of truth.

## 5. Evaluation on real statements

- **Private set:** the user's real statements for the months in scope, at the path in `PRIVATE_EVAL_DIR` (default `data/private/`, gitignored). Never committed — this repo is public.
- **Where it runs:** locally by default — it needs the real files and API keys. `make eval-private` prints only aggregate metrics and per-statement status, never row contents, and writes results inside the private dir. That keeps the choice of where it runs open without changing the code.
- **Golden labels, cheaply:** run the extractor, export rows to CSV, correct them by hand once → `data/private/labels/*.csv`. Where the bank offers both a structured export and a PDF for the same month, the export is ground truth for the PDF (principle 13).
- **Metrics per statement** (principle 12 — never just the aggregate): row recall and precision, amount exact, sign exact, date exact, currency exact, `balance_status`. Run on whole statements, not samples (principle 11).
- **The label-free metric:** the share of statements with `balance_status = ok`. It works on any new statement, labeled or not, and is reported on every run.
- **Synthetic set, made realistic:** extend `generate_samples.py` with day-first dates, comma decimals, Débito/Crédito + Saldo columns, multi-page PDFs with repeated headers, wrapped descriptions, a two-currency card statement, an `.xls` file and statement images. Fix the balance-row labels (F6). Include images in the normalize eval (F7).
- **Comparison runner:** the v1.5 runner (one change at a time, quality and cost side by side) is reused for the LLM rung's model and prompt experiments.

## 6. Phases

Ordered so that the first phase measures before anything changes; each phase ships on its own. Inputs are mainly PDFs, so PDF comes first and the other formats last.

1. **Measure.** `Statement` model + migration; statement header extraction; balance check and diagnostics run on the **current** extraction, which stays unchanged. Private set loaded. Output: the honest baseline per statement.
2. **Parsing module + PDF.** `shared/parsing.py`; per-bank PDF profiles for the banks in the private set; LLM rung hardened (transcribe-only, whole-statement header, text + image, anchors, page counts, targeted retry); balance rows out of transactions; cache key change; synthetic data and labels updated.
3. **Report correctness.** `kind`, transfer and card-payment pairing, installments as billed (§4.1), configurable report currency (§4.2), same-statement-twice dedup, unconverted line; aggregations switch to `kind`.
4. **Other formats.** Deterministic XLSX/XLS/CSV reader; statement images.

## Acceptance criteria

- Every statement in the private set has a `Statement` row with a `balance_status`, and every file that produced nothing appears in diagnostics with a reason — zero silent losses.
- On the private set: ≥ 95% of statements `balance_status = ok`; on labeled statements, row recall ≥ 99% and amount + sign exact ≥ 99%.
- No row's currency comes from the `base_currency` default.
- The expense total for a month excludes own-account transfers and card payments, and states any unconverted amount.
- Installment rows never appear as recurring charges.
- Changing `BASE_CURRENCY` changes report totals without re-extraction, and no query sums amounts converted to different currencies.
- The synthetic eval covers day-first dates, comma decimals, debit/credit columns, multi-page PDFs and statement images, and still passes.
